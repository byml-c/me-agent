# Me.Agent PRD：Graph-native Personal Agent

## 1. 产品概述

### 1.1 产品名称

**Me.Agent**

### 1.2 产品定位

Me.Agent 是一个以个人认知图为核心的长期陪伴型 Agent。它将用户的想法、项目、记忆、文件、脚本、生活事件、任务和工作流统一表示为无向图中的节点，并通过局部视野、差序格局式上下文组织和图上更新机制，为用户提供可持续演化的个人认知运行时。

Me.Agent 不以传统文件夹、标签或静态知识库为中心，而以“图上的节点与连接”为核心。用户可以与 Agent 聊工作、生活、研究、随想，Agent 会根据当前对话自动激活附近节点，辅助用户整理、联想、拆分、聚合和生成新的工作区节点。

### 1.3 核心理念

1. **认知即图**
   一切认知对象都可以被建模为图上的节点。
2. **万物皆节点**
   概念、记忆、文件、项目、脚本、任务、随想、关系解释、工作区都可以是节点。
3. **底层无向图，局部可视化**
   底层结构保持自由的无向图；树状结构、工作区、时间线、任务板只是局部视图。
4. **差序格局式上下文**
   Agent 的上下文不是全局检索，而是以当前节点为中心，按照图距离、边权、访问频次、时间衰减和语义相关性组织局部视野。
5. **图上生长**
   节点和边不是一次性定义完成，而是在使用过程中被访问、强化、弱化、拆分、聚合和归档。
6. **Reader / Writer 分离**
   Agent 的上下文读取和图结构更新应当分离，避免边回答边污染记忆。

## 2. 目标用户

### 2.1 核心用户

* 有长期项目管理需求的研究者、学生、工程师、创作者；
* 习惯使用 Obsidian、Logseq、Notion、Tana 等工具的个人知识管理用户；
* 希望将工作、生活、兴趣和随想统一到一个认知系统中的用户；
* 需要长期记忆、项目上下文、自动整理和主动联想的 Agent 用户。

### 2.2 典型用户场景

1. 用户和 Agent 讨论一个研究项目，Agent 自动调动相关论文、实验、代码、TODO 和过往对话。
2. 用户记录一个生活随想，Agent 发现它和某个工作项目有关，提出候选连接。
3. 用户长期围绕一个概念讨论，Agent 判断该节点过大，建议拆分为多个子节点或升级为工作区。
4. 用户准备启动一个新项目，Agent 从已有概念中生成一个新的工作区节点。
5. 用户进入某个节点，Agent 展示该节点的局部视野，包括相邻节点、强连接节点、最近访问节点和候选操作。

## 3. 产品范围

### 3.1 MVP 范围

MVP 目标是实现一个可用的本地或单用户版 Me.Agent，支持以下核心闭环：

1. 创建节点；
2. 创建无向边；
3. 与 Agent 对话；
4. Agent 基于当前节点的局部图上下文回答；
5. Agent 自动记录对话 episode；
6. Agent 提出图更新 proposal；
7. 用户确认或拒绝 proposal；
8. 前端展示局部图视野；
9. 支持节点升级为工作区；
10. 支持大节点拆分建议。

### 3.2 非 MVP 范围

以下能力不作为第一阶段必须实现：

* 多用户协作；
* 复杂权限系统；
* 移动端 App；
* 完整插件市场；
* 复杂多 Agent 编排；
* 自动执行高风险外部操作；
* 企业级知识库导入；
* 跨设备实时同步。

## 4. 核心概念定义

### 4.1 Node：节点

节点是 Me.Agent 的基本单位。任何对象都可以是节点。

节点可以表示：

* 一个想法；
* 一个项目；
* 一个工作区；
* 一段记忆；
* 一次对话；
* 一个文件；
* 一个脚本；
* 一个任务；
* 一个问题；
* 一个兴趣；
* 一个生活事件；
* 一个关系解释。

节点不需要复杂类型系统，但可以有少量状态字段。

### 4.2 Edge：边

边是节点之间的无向连接。MVP 中边不设计复杂语义类型。

边主要表达：

* 两个节点经常一起被访问；
* 两个节点存在用户确认的关联；
* 一个节点启发了另一个节点；
* 一组节点属于同一个局部上下文；
* Agent 推测两个节点可能相关。

边的语义可以通过节点正文、关系节点或局部工作区来表达，而不是通过复杂边类型表达。

### 4.3 Workspace：工作区节点

工作区不是单独的数据类型，而是一个带有 `is_workspace = true` 标记的普通节点。

工作区节点用于组织一批相关节点，使其形成一个临时或长期的局部认知场。

例如：

* Me.Agent；
* UniVTAC；
* 研究生申请；
* Arch Linux 调试。

### 4.4 Episode：事件节点

Episode 是由一次对话、一次导入、一次随想或一次操作生成的原始记录节点。

Episode 的作用是保存原始上下文，避免 LLM 抽取造成信息损失。

### 4.5 Proposal：更新提案

Agent 不直接修改高风险图结构，而是生成 Proposal。

Proposal 可以包括：

* 新建节点；
* 修改节点；
* 删除节点；
* 拆分节点；
* 合并节点；
* 新建边；
* 删除边；
* 强化边；
* 弱化边；
* 创建工作区；
* 将节点升级为工作区。

## 5. 产品功能需求

### 5.1 节点管理

用户可以创建、编辑、归档和查看节点。

节点可以通过以下方式创建：

* 手动新建；
* 对话中由 Agent 自动创建；
* 从文本中抽取；
* 从文件导入；
* 从已有节点拆分；
* 从多个节点聚合为工作区。

节点支持以下核心操作：

* 编辑标题和正文；
* 查看访问次数和最近访问时间；
* 查看相邻节点；
* 查看相关 episode；
* 查看节点历史；
* 归档节点；
* 升级为工作区；
* 接受 Agent 的拆分建议。

MVP 中优先支持归档，不建议物理删除。物理删除应作为高级操作，并需要二次确认。

### 5.2 边管理

用户可以创建和删除无向边。

边可以由以下方式产生：

* 用户手动连接；
* Agent 自动创建候选边；
* 节点共同进入上下文时自动强化；
* 工作区生成时批量创建；
* 文件或文本导入时自动生成。

Agent 推测但用户未确认的边应标记为候选边。候选边可以进入低权重上下文，但前端应以弱视觉形式展示，用户可以确认、拒绝或忽略。

### 5.3 对话与 Agent

用户可以与 Me.Agent 进行自然语言对话。

Agent 应支持：

* 回答问题；
* 总结节点；
* 解释局部图；
* 提出关联；
* 创建节点；
* 修改节点；
* 生成工作区；
* 拆分大节点；
* 记录随想；
* 查询历史记忆。

每次对话都应有一个或多个当前锚点。锚点可以来自用户显式指定、当前打开节点、最近活跃工作区、对话中提到的节点、语义检索最相关节点或 Agent 推断的主题中心。

### 5.4 差序格局上下文

Agent 的上下文由 Context Reader 生成。

上下文选择因素包括：

```text
activation_score(node) =
  semantic_relevance
  + graph_proximity
  + edge_weight
  + access_frequency
  + recency
  + workspace_importance
  - staleness
  - privacy_penalty
```

上下文应分层组织：

1. 当前锚点：详细内容；
2. 一跳强连接节点：摘要 + 关键字段；
3. 二跳节点：短摘要；
4. 远处候选节点：标题索引；
5. 原始 episode：按需拉取；
6. 脚本节点：默认只暴露接口，不暴露完整代码。

### 5.5 Graph Writer

Graph Writer 根据对话结果和上下文生成图更新 proposal。

Proposal 类型包括：

```text
create_node
edit_node
archive_node
split_node
merge_node
create_edge
remove_edge
strengthen_edge
weaken_edge
create_workspace
promote_to_workspace
```

低风险操作可自动执行：

* 更新节点访问时间；
* 更新节点访问次数；
* 强化已存在边；
* 创建 episode 节点；
* 创建低权重候选边；
* 保存对话摘要。

高风险操作需要用户确认：

* 删除节点；
* 归档重要节点；
* 合并节点；
* 拆分节点；
* 将节点升级为工作区；
* 执行节点脚本；
* 修改脚本；
* 创建大量边；
* 修改高权重节点正文。

### 5.6 节点脚本

节点可以包含脚本引用，用于读取、计算、转换或执行操作。

脚本类型：

1. `read_script`：读取信息；
2. `transform_script`：转换或计算；
3. `action_script`：修改外部环境。

MVP 中脚本默认不自动执行。所有脚本执行记录进入 event log。

### 5.7 事件日志

所有重要操作都应记录为 Event。

事件日志用于：

* 回滚；
* 审计；
* 时间线展示；
* 节点演化分析；
* Agent 自我反思；
* 调试上下文污染问题。

## 6. MVP 验收标准

### 6.1 图操作

* 用户可以创建、编辑、归档节点；
* 用户可以创建和删除边；
* 系统可以展示当前节点的二跳局部图；
* 边权可以根据访问自动更新；
* 候选边可以被确认或拒绝。

### 6.2 Agent 对话

* 用户可以在某个节点或工作区下与 Agent 对话；
* Agent 能展示本轮使用的上下文节点；
* Agent 能基于局部图而不是全局文本检索回答；
* Agent 能自动创建 episode 节点；
* Agent 能提出至少三类 proposal：新建节点、创建边、拆分节点。

### 6.3 工作区

* 节点可以被标记为工作区；
* 工作区页面可以展示局部图、最近活动、相关节点；
* Agent 可以建议将节点升级为工作区。

### 6.4 安全和可控

* 高风险操作必须用户确认；
* 所有图更新必须进入 event log；
* 用户可以查看节点历史；
* 用户可以拒绝 Agent 的图更新建议。

## 7. 成功指标

### 7.1 产品指标

* 用户每天新增节点数；
* 用户每天与 Agent 对话轮数；
* 用户接受 proposal 的比例；
* 用户拒绝 proposal 的比例；
* 节点二次访问率；
* 工作区复访率；
* 候选边确认率；
* Agent 回答中上下文命中率。

### 7.2 体验指标

* 用户是否能理解当前 Agent 使用了哪些节点；
* 用户是否能控制图的更新；
* 用户是否觉得图结构在变清晰；
* 用户是否减少了重复解释项目背景的次数；
* 用户是否愿意把长期项目放进 Me.Agent。

### 7.3 技术指标

* Chat API 首 token 延迟；
* Context Reader 查询耗时；
* 局部图加载耗时；
* Proposal 生成耗时；
* Embedding 更新耗时；
* Graph operation 失败率；
* Event log 完整性。

## 8. 风险与应对

### 8.1 图过度膨胀

风险：Agent 自动创建太多节点和边，导致图混乱。

应对：

* 自动创建的边默认是候选边；
* 低活性节点自动沉降；
* 定期生成整理建议；
* 大节点拆分需要用户确认；
* 默认展示局部图，不展示全局图。

### 8.2 上下文污染

风险：Agent 使用了错误节点，导致回答偏离。

应对：

* 展示 used_context；
* 用户可以移除错误上下文节点；
* Graph Writer 和 Context Reader 分离；
* 候选边低权重；
* 引入事件回滚。

### 8.3 用户认知负担过大

风险：用户需要理解太多概念和操作。

应对：

* 不引入复杂节点类型；
* 不引入复杂边类型；
* 默认只显示节点、边、工作区；
* 高级操作隐藏在 Agent 建议中；
* 通过自然语言完成大部分操作。

### 8.4 LLM 错误更新

风险：LLM 错误修改图结构。

应对：

* 高风险操作需要确认；
* 所有操作进入 event log；
* 支持回滚；
* 保留原始 episode；
* 提案中展示理由和影响范围。

### 8.5 脚本安全

风险：节点脚本可能执行危险操作。

应对：

* 默认禁用自动执行；
* 沙盒运行；
* 权限分级；
* 超时限制；
* 执行前展示影响范围；
* 记录执行日志。

---

## 9. 一句话总结

Me.Agent 的核心不是“一个带 AI 的笔记软件”，而是一个以无向认知图为底层结构的个人 Agent Harness。它通过差序格局式上下文组织、图上更新提案、节点演化和工作区生成，让用户的工作、生活、兴趣和记忆在长期交互中自然生长为一张可操作的个人认知图。
